01 · Evaluation Methodology

How we decided what "good" even means

Before touching any model, two fixes to how we SCORE models turned out to matter as much as anything downstream.

F1-optimal thresholding Worked
ProblemEvery model used a flat 0.5 cutoff. Isolation Forest's F1≈0.70 looked fine — until we noticed FPR≈0.996 (it was flagging almost everything).
WhyF1 for a zero-skill always-positive classifier = 2·prevalence/(1+prevalence). At 54% attack, that's F1≈0.70 — indistinguishable from a coin that always says "attack."
before: fixed 0.5 cutoff → after: threshold chosen per-model to maximize F1 on held-out training data
TakeawayNecessary, but not sufficient alone — see the FPR cap below.
FPR cap, evidence-based Worked
ProblemWithout a cap, F1-maximization can converge to "flag almost everything" when a model can't discriminate — exactly what happened above.
MethodBuilt operating_curve.py to sweep candidate caps (0.01–1.0) and measure real F1/Precision/Recall/FPR trade-offs on RF, instead of guessing.
before: MAX_FPR=0.10 (guess) → after: MAX_FPR=0.05 — F1 peaked here (0.863), declined for looser caps
TakeawayA swept, justified number beats a guess — and it revealed F1 actually gets WORSE past a certain FPR budget, not just "more expensive."
02 · Model-Specific Interventions

Three targeted fixes — one confirmed, one rejected (usefully), one partial

Isolation Forest — novelty-detection mode Hypothesis rejected — still useful
HypothesisCAM-LDS's mixed 46/54 training population dilutes what the model learns as "normal."
MethodFit Isolation Forest only on confirmed-benign rows instead of the full mixed fold (semi-supervised — uses labels to pick the fit subset, not to fit the trees).
AUROC before: 0.532 → AUROC after: 0.555 — essentially unchanged
TakeawayThe hypothesis was wrong, and that's informative: the failure isn't WHAT the model trains on, it's the random-split isolation mechanism itself. Confirmed independently later (see §03).
log1p preprocessing Partial / mixed
HypothesisIsolation Forest picks split points uniformly at random — skewed features waste splits in the dense region. RF/XGBoost choose splits by sort order, so this should be a no-op for them.
ResultRF confirmed unaffected (0.9994→0.9994, proving the no-op theory). Isolation Forest genuinely changed — but direction was data-dependent, not a guaranteed win (slightly hurt in one synthetic test).
Correction issuedThe "no-op for XGBoost" claim was overstated — XGBoost's tree_method="hist" is approximate, not exact, so it's NOT fully invariant to monotonic transforms. Likely explains later single-run instability.
TakeawayKept on (harmless for RF/XGBoost, roughly neutral elsewhere) — but reported honestly as untested-positive, not oversold.
CNN degenerate-split guard Partial fix
ProblemCasinoLimit is 99.6% duplicated (356 unique patterns / 91k rows). CNN's inner validation split occasionally landed on an unrepresentative slice, producing a garbage threshold.
before: F1 swinging 0.11–0.86, FPR 0.003–0.98 → after: reduced frequency, not eliminated — stress test held 0.72–0.96, but 1/15 real repeats still collapsed
TakeawayGenuine improvement, reported honestly as a mitigation rather than a fix.
03 · Engineering Fixes

Not modeling changes — but nothing runs without them

XGBoost thread oversubscription Engineering fix
SymptomXGBoost completed only 2–3 of 15 CV repeats in a 2-hour budget where RF, doing equivalent work, finished all 15.
CauseXGBoost defaulted to spawning threads for every core on the shared SLURM node, not the 4 allocated to the task — severe thread thrashing under concurrent jobs.
before: 2–3/15 repeats in 2hrs → after: 8–12/15 in 3hrs (4–5x speedup) after pinning n_jobs=4
04 · The Headline Experiment

CAM-LDS corpus regeneration: 54.0% → 28.7% attack rate

The extraction pipeline had only ever scanned 98 of 8,103 available raw log files (1.2%) — find_audit_logs() only looked inside scenario_*/ directories, never manifestations_filtered/. Verified via md5sum that the additional 2,252 files are genuinely independent repeated trial executions, not duplicates (19 separate trials of one scenario alone). Regenerated CAM-LDS combining both sources, targeting the original ~90.8k row count.

Attack rate before: 54.0% → after: 28.7% — using the full corpus, at the same ~90.8k row count

Within-dataset: Isolation Forest, CAM-LDS

AUROC moved meaningfully (real, ~2.5 std above the original mean). F1 barely moved — expected, since precision naturally falls as attack becomes a genuine minority even when ranking improves. AUROC is the metric that actually tests the hypothesis.

Cross-dataset: train on CAM-LDS, test on CasinoLimit — the real headline

Three of four models went from near-total ranking inversion to genuinely strong transfer. Isolation Forest is the clean negative control: the same fix, zero effect — independently confirming §02's novelty-mode finding that its failure is mechanistic, not distributional.

Recalibration experiment: a clean, theory-confirming split

First attempt used a buggy calibration split (GroupShuffleSplit allocated 5% of unique GROUPS, collapsing to just 35 rows on Casino's 356-group duplication). Fixed with a row-proportional split (row_proportional_group_split(), verified leak-free on synthetic Casino-scale data: 35→7,586 rows for the same request). With a real sample (5,398–8,259 rows), the result is decisive.

Recalibration requires a genuinely good ranking to exploit; it cannot manufacture one.
05 · Considered, Not Pursued

Deep Autoencoder as an Isolation Forest alternative

The brief allows either Isolation Forest or a Deep Autoencoder for the unsupervised paradigm. Given two independent experiments (novelty mode, and the corpus regeneration's negative-control result) both point to Isolation Forest's failure being mechanistic rather than distributional, an autoencoder — a different, gradient-based approach to learning "normal" — is a reasonable third test of the same hypothesis. Not built: the existing evidence is already strong without it, and remaining required deliverables (sample-level error analysis, hybrid cascade, LLM triage layer) took priority given project timeline.
